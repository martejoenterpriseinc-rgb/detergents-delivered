# Customer account and support increment — September 9, 2026

This extends the retained Render application at `0da05682ce1c4c90c79bcdfadede361f3e18ec8b`. It does not rebuild Sites, replace authentication, touch the separate backend checkpoint, or modify Martejo/BidSmooth.

## Implemented in this branch

- Customer account: full pages for name/phone edits, password change, and email/SMS notification preferences. Account creation and customer creation dates come from the original database records. Email/roles/verification are not editable in profile requests. Existing Owner/Admin + Customer membership remains intact, with an Admin dashboard link for staff.
- Regular password change requires the current password, 12+ characters, a 72-byte bcrypt limit, and confirmation. Five failed current-password attempts lock this operation for 15 minutes. Password replacement, session version increment, and redacted audit are atomic. All existing JWT sessions fail on their next authoritative server read; old versionless sessions remain valid only at version zero. Credential login carries the version observed during password verification to reject concurrent stale sign-ins. OAuth-only accounts use their provider; no reset or account-linking shortcut is added.
- The household account no longer consumes localStorage demo orders. Orders and route dates are queried by the session user's active customer ID, never ZIP. Paid order amounts, line snapshots, addresses and scheduling records are read-only. Planned arrival is labeled as a route schedule, not Waze/live ETA. Driver transitions and private photos remain a separate unaccepted integration.
- Loyalty Club is a clearly labeled prelaunch display. No points, tiers, discounts, enrollment or rewards are invented. Quarterly-only/payment-at-purchase copy replaces the conflicting four-week example; subscription billing is not activated.
- Every saved order has Report a problem. Contact us opens an account-owned support ticket. Customer/staff conversation persists in PostgreSQL. Staff can mark Open / In progress / Waiting for customer / Resolved. Customer replies reopen tickets. Resolving a ticket does not refund, pay, reschedule or change an order.
- Admin dashboard has a clickable active Support tickets KPI. Admin/Super Admin support page has status KPIs, lookup, status filtering, sorting, pagination and filtered CSV export. CPA/inventory/driver roles have no support access. Every KPI links directly to its counted subset.
- New HTTP endpoints enforce session/credential state and exact Origin for JSON writes, reject unknown mutation fields, cap actual body bytes, redact unexpected failures, and use no-store responses. Service methods recheck database ownership/roles. Writes and audit are transactional. Ticket/reply retries are idempotent; changed-key payloads and stale ticket versions conflict rather than overwrite history. Account/ticket row locks serialize competing writes. Ticket/reply rate limits use database counts under a user lock.

## Deliberate remaining gaps

Email/SMS delivery is not connected: toggles persist preferences only, and support replies are in-app. Sender verification, phone/email verification, unsubscribe/legal delivery policy and reliable workers remain provider acceptance gates. No messages are sent by these changes. Login email changes and delivery address changes require the independent identity/eligibility workflow; the profile page directs these to support and does not rewrite paid bookings. Loyalty program rules, Stripe/tax, quarterly billing, immutable receipt/PDF, driver/proof-photo workflow and full commerce launch remain unaccepted.

## Migration and operational review

New additive migration: `20260909120000_customer_account_support`. Adds three User security columns with zero/null defaults, two Customer preference columns defaulting off, SupportStatus, SupportTicket and SupportMessage with FK/unique/index constraints. Existing four migrations are unchanged. No existing business rows are deleted, repriced, reseeded or reassigned. New preference defaults are not inferred consent. Existing roles, passwords, emails and creation dates remain unchanged. The API owns order/customer matching; no ticket can be submitted for a different customer's order. Support table FK restrictions protect conversation history. Service queries do not expose password hashes, storage keys, staff-only notes, or other customers' tickets.

Prestart remains read-only and refuses pending migrations. Readiness now probes the added columns/tables. The previous owner approval for an exact startup deployment excluded migrations, so this change has NOT been deployed or migrated on Render. Before any staging migration: owner approves the exact tested revision and migration, operator captures/verifies a restorable backup/schema inventory, reviews the additive SQL and lock impact, applies this one migration in the private staging runtime, repeats history/readiness checks, then deploys the same revision. No automatic migration in startup. An app rollback may retain the additive tables/columns; do not reverse-delete support history or downgrade session checks after a password rotation (old binaries do not enforce sessionVersion). Prefer forward repair; any older-binary recovery requires session invalidation/review.
