# Application financial workflows

This increment continues PR 85. It adds application behavior; intended provider connections and hosted acceptance remain deferred. Production activation flags are unchanged.

- Cash/Zelle receipts arriving late, after revocation, after canceled reservations, or for the wrong amount are recorded in REVIEW. Staff can approve an exact, still-reserved payment after renewed authorization, record an actual return with its unique reference, or reschedule a reserved delivery within the original area's calendar and shared vehicle capacity. Return does not initiate a transfer. Released reservations cannot be resurrected as paid orders. Verified tax IDs are saved before delivery finalization, so a missed route retains GET-only tax recovery.
- Failed merchandise refunds can verify an existing positive Stripe Tax adjustment against the original report-backed tax reversal and each original line. They can then prepare a separate QuickBooks SalesReceipt restoring the exact cash, net and tax of the posted RefundReceipt, using its original company/accounts. Original receipts, compensation and rewards remain intact. Confirmation resolves the original receipt warning; uncertain corrections use the existing GET-only worker recovery.
- Tip journals separately track Stripe clearing, the driver payout bank, tips payable, tax liability and driver recoverables. Staff reviews five active USD accounts, prepares an immutable balanced adjustment, and submits it once. Refunds and payout reversals produce deltas against the last confirmed journal. A failed refund with previously matched tax needs a verified positive tax correction before accounting can restore that tax balance. The existing QuickBooks worker also checks tip journals.
- Explicit tip-refund and manual-refund-tax retries reuse the original payload, reference and idempotency key only within 23 hours of the original claim. Provider calls recheck the deadline before creation. They do not create a new local request or release uncertain funds. Outside that window, recover the existing transaction using provider evidence; empty search results never prove that a financial request was not created. QuickBooks uncertainty remains GET-only.

Tip posting requires `DD_QBO_TIP_POSTING_ENABLED=true` and `DD_QBO_TIP_POSTING_COMPANY=<sandbox|live>:<realm>`, in addition to the existing environment, OAuth and finance authorization checks. Review an intended clearing bank, driver payout bank, tips payable liability, tax liability and driver receivable account; IDs are never inferred or provisioned automatically.

Tax correction matching reads an existing provider adjustment. It does not manufacture tax evidence or automatically apply off-Stripe tax reversals to Checkout payments. The provider's intended failed-refund correction must be confirmed during deferred API acceptance. See Stripe's [transaction reversal API](https://docs.stripe.com/api/tax/transactions/create_reversal) and [reversal cancellation example](https://docs.stripe.com/tax/off-stripe#cancel-a-partial-refund). A real tax correction is not proven by returned money or synthetic fixtures.

Three additive migrations extend manual review states, create immutable tip journal history and permit evidence-backed receipt corrections. All prior SQL remains unchanged. The release manifest contains their checksums. Migration replay in CI uses an isolated database; hosted database recovery and retained-record comparison remain separate release requirements.

Validation is recorded on the final PR revision. Native cases cover concurrent requests, tax mismatch, retained original receipts, stale provider responses, review authorization, returned funds, rescheduling and immutable journal claims. All external responses in these cases are synthetic.
