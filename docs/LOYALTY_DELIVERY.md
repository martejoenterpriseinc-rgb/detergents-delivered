# Loyalty, live account tiles and owner entry — September 9, 2026

Increment on account/support PR #13 at `987dfaa8ec326c5ca7739e3008e0f850621e63ff`. Retains this GitHub/Render application and the existing authentication/database. Sites, the separate saved backend, Martejo, BidSmooth, production, DNS, providers and hosted resources are unchanged.

## Implemented

- Staff's default sign-in target resolves persistent roles after authentication: Admin/Super Admin/other existing admin-shell roles go to `/admin`; customers go to `/account`. Explicit safe local return paths remain honored; external and backslash return paths are rejected. Required credential-change gating remains. No personal email is hardcoded and no role, password or account merge occurs. Admin header **View as customer** opens the same user's household account; **Back to admin** returns to staff mode. This is not impersonation.
- Account delivery and Loyalty Club occupy identical 128px tiles. Delivery polls the owned order read model every 15 seconds while visible, refreshes on focus/reconnection, aborts stalled requests, and labels unavailable updates instead of pretending old data is fresh. Color is accompanied by status text. Source is saved order/route schedule, not Waze ETA, GPS or live driver tracking. Existing order transitions drive the widget; this does not implement driver transitions/photo uploads.
- Customer Loyalty Club shows real dollar-credit balance, held credits, lifetime referral earnings, the latest 100 link records and latest 100 ledger entries. New invitation URLs/codes are unguessable. Copy/share actions are recorded only after browser success; they never claim recipient delivery/read confirmation. One invitation accepts one new account. No messages are sent automatically.
- Account-owned claims require a verified email, no prior purchase, distinct customer/contact identity, a valid unexpired unclaimed invitation, and enabled program settings. Same ZIP is not identity. Duplicate claims/requests cannot create duplicate referrals; changed idempotency requests fail. Referral amounts, minimum purchase and program version are snapshotted at claim. No claim creates credits.
- Admin Loyalty program configures enable/pause, dollar reward amounts for both parties, minimum merchandise purchase, invitation lifetime and rewarded-referral count limit. Version checking rejects stale settings saves. Status KPIs open full referral/ledger pages, with lookup, filters and pagination. Admin/Super Admin role checks protect every control and endpoint.
- Review qualifying purchase issues credits only for a first paid USD order meeting its snapshot and carrying matching persisted signature-verified provider evidence. New PaymentEvent.verifiedAt defaults NULL: old payment rows are never inferred to be verified. The review action cannot collect payment or mark an order paid. A refunded/cancelled qualifying purchase produces compensating entries once; previous awards/spends remain immutable. A deficit blocks further spending until covered by earnings. Automated reconciliation is still pending the provider/worker integration.

## Rewards and checkout boundary

The retained checkout is still not connected to real/sandbox payment, tax, approved eligibility, inventory/capacity reservation or receipt finalization. It now requires a signed-in account and cannot create a misleading local order confirmation. Its retained form/layout is a preview, with purchasing disabled. **Apply rewards** calls a server-owned catalog/balance quote; posted prices or balances are rejected. Its notice states the amount that would apply and remain, and that no rewards were used. It quotes merchandise only; it is not a final tax/payment quote and never reserves/spends credits. Cart edits invalidate the displayed quote.

Internal `reserveOrderRewards`, `commitOrderRewards`, and `releaseOrderRewards` prepare the integration boundary. They are not exposed by public endpoints. Customer wallet and order locks serialize holds/spends; unique keys protect retries. Credit use is `min(available credits, final amount due)` in integer cents. Order totals/tax/discount history stay unchanged: the prepared redemption represents credit tender, not a price rewrite. Confirmed commits return used amount and remaining available balance for the future successful-checkout notice. A hold cannot auto-expire while an uncertain payment might complete. Release requires a cancelled order and no pending/authorized/captured payment. Changed totals, reversed balances, missing payment evidence or released holds fail closed. A zero-cash order still requires the future unified stock/capacity/order/receipt finalization transaction; this helper alone does not make a sale.

Remaining acceptance gates: actual payment/webhook signature adapter, verified account delivery/approval, tax and final credit treatment, unified checkout transaction, payment-failure recovery, automatic award/reversal processing, partial/full purchase refund allocation and restoration of spent credits, reliable workers, provider sends/receipt history and financial reconciliation. The internal ledger helpers and synthetic verified-payment fixtures do NOT prove a real Stripe sandbox workflow. Public email verification is also unconnected; no workaround or inferred verification is added. Admin can save settings without granting verification to any user. Full fraud controls across aliases/households remain a commerce acceptance item.

## Migration and review

New additive migration `20260909140000_loyalty_rewards` adds program/link/ledger/reservation tables, extends the existing Referral model and adds nullable provider-verification time. All five previous migration files remain unchanged. Existing customer/order/payment amounts, emails, roles, passwords, addresses and paid bookings are untouched. Database checks constrain amounts/signs/settings; a trigger rejects RewardEntry updates/deletes. Corrections append entries. Foreign keys and unique indexes retain ownership/history and idempotency.

Account/API changes retain authentication, credential gating, same-origin JSON writes, strict schemas, bounded request bodies and redacted errors. Staff actions recheck DB roles. Program/award/reservation mutations and audits are transactional. Referrer/friend wallets lock in sorted order for award/reversal; checkout uses wallet then order lock. No externally callable spend/verification/admin-grant shortcut exists. Readiness probes include the new tables/columns; prestart remains read-only. No migration is run automatically at app startup.

Not migrated/deployed to Render. Existing staging approval excluded new migrations. Rollout requires approval of the final tested revision and both unapplied additive migrations after inventory/backup verification, one private staging migration operation, readiness checks and that exact revision's deployment. Do not merge/downgrade blindly; retain account session-version security from PR #13 and immutable reward history. Production remains **NO LAUNCH**.
