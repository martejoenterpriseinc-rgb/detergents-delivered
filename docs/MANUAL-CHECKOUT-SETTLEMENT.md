# Approved cash / Zelle reservation and settlement

This increment extends the authoritative checkout. It does not introduce a parallel order, stock, reward or delivery system. A shared finalizer preserves the existing card settlement behavior and is also used after manual receipt and tax evidence are confirmed.

`DD_MANUAL_PAYMENTS_ENABLED=true` permits offering approved methods. Live use additionally requires `DD_LIVE_MANUAL_PAYMENTS_ACCEPTED=true`. Both stay off until the complete manual workflow and provider acceptance pass. API connections remain deferred until application construction is complete.

Customer checkout retrieves only the available approved methods. The reservation transaction checks active purchase eligibility, approval, expiry and limit while holding the customer lock, then uses the same quote, FIFO reservations, reward holds and vehicle capacity checks as online payment. Method becomes fixed on reservation; Stripe payment settlement cannot consume a manual checkout. Existing card workers skip manual reservations. Customers may cancel an unpaid manual reservation once, releasing stock/cost/reward holds. Recorded funds cannot be cancelled as an unpaid reservation.

Payments → Cash / Zelle settlements lists the latest 100 manual checkouts in the configured account/environment. Admins confirm an exact received amount with a receipt reference, notes and timestamp. Per-checkout and per-method/account/environment receipt uniqueness, immutable request hashes, access checks and an atomic audit prevent duplicate or changed receipts. CPA access is read-only. Receipt confirmation rechecks current approval and reservation time. Exceptions outside those bounds still need an explicit received-funds review workflow before live use.

Tax reconciliation durably claims the receipt before provider posting. It posts the original tax calculation with a fixed reference, receipt timestamp and idempotency key. Retries without a known transaction ID stop after 23 hours; staff can supply an existing transaction ID for strictly bound retrieval. The provider transaction must match account, environment, receipt metadata, destination, original line references, quantities, net amounts, product tax codes, exclusive tax and total tax. Truncated or mismatched evidence stops settlement. No tax rates or registrations are invented.

After verification, a transaction locks checkout/customer/order/vehicle and confirms delivery is still available and rewards remain held. The shared finalizer consumes FIFO inventory and rewards, records one MANUAL payment/event, creates one delivery stop, updates the order and records the original settlement audit. The original quote is retained; accepted tax transaction evidence lives on the manual receipt. Customers can print the original receipt. An interrupted provider call or failed finalization leaves recorded money pending reconciliation and does not invite another payment. Late/departed delivery reservations need a dedicated rescheduling review before they can be completed.

The additive `20260917020000_manual_checkout_settlement` migration adds a payment-method discriminator (existing checkouts default to STRIPE) and a constrained ManualCheckoutSettlement table. No older migration SQL is changed. It has not been applied to hosted databases.

Validation added: provider tests cover stable posting parameters, account/mode/address/line/tax mismatches, truncated/duplicate evidence and expired retry recovery; native checkout tests cover method isolation, authority, duplicate received-money requests, one payment/stop, inventory consumption, original receipts, interrupted tax posting and unpaid cancellation. Existing full checkout tests exercise the extracted finalizer. Full CI and browser acceptance must be recorded separately.

Still required before enabling manual payments: received-funds exceptions for revoked/expired approvals and late receipts; manual tax reversal/refund initiation/recovery; source-verified CPA/QuickBooks export support for MANUAL payments; background manual settlement recovery and safe delivery rescheduling; browser acceptance and intended sandbox/live provider acceptance. These gaps remain visible rather than silently marking manual payments ready.

Provider reference reviewed for this implementation: [Stripe Tax transaction from calculation](https://docs.stripe.com/api/tax/transactions/create_from_calculation). The installed pinned SDK declarations were also checked. Tests use synthetic provider evidence and do not establish real provider acceptance.
