# Durable receipt drafts

Finance staff can prepare a receipt draft from the existing original-source review, inspect saved drafts and cancel an unsent draft. Each draft permanently retains the full original sale/refund evidence, customer/product/tax/clearing mappings, compiled payload, request identity and document reference. Preparation replays one actor-scoped request and only one active export may exist per source, even across companies. A canceled draft remains in history; a fresh request can prepare a new draft.

The new `QboReceiptExport` migration adds restricted foreign keys to the original order and optional refund adjustment, immutable source/mapping/payload and forward-only status constraints, permanent provider identities/timestamps, unique company/entity/provider references and a source uniqueness index. No existing migration is edited. Apply this only as part of the reviewed release and retained-record/backup workflow; the existing two-migration deployment script does not authorize it.

A cash refund draft requires a matched settlement, its original posted sale receipt in the same company, unchanged original sale evidence and the exact original sale mapping. Current mapping changes cannot change the refund's accounts, customer, items or tax treatment. Database checks also enforce the original-sale relationship and matching mapping. Unverified tax, compensation and reward-only entries cannot enter this cash receipt path. Restored rewards stay in their own ledger and are not added to refund cash.

Authorization, per-order locks, duplicate-source checks, preparation and audit creation run transactionally. Audit failures roll back the draft. CPA users may read but cannot prepare/cancel. Cancellation is idempotent, retains the draft and audit, and is rejected after submission. API actions use existing account/CSRF/JSON validation. Review responses omit the original private street address even though the immutable internal payload retains the destination for provider reconciliation.

This increment does not implement submission or scheduled reconciliation. There is no submit action, provider write or automatic posting. Those steps must recheck current connection, company/account/item evidence and original source, durably claim once before any provider call, and hold uncertain outcomes for read-only recovery. Synthetic source/provider adapters in the draft integration tests are explicitly isolated; the separate original-source integration suite validates actual ledgers. Neither establishes real provider acceptance or Go Live.
